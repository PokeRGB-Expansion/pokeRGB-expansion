# Species IDs, presets and large rosters

## Build decision

Keep one source tree. Minimal, Core and Extended are named sets of build settings. Red, Blue and cosmetic Green select a separate game variant. A developer can start with Core rules, add hundreds of species, keep one Special stat, and explicitly select the stock type chart and trainer AI. A developer can also select an improved AI with the 151-species roster. Neither combination requires a permanent branch.

**Use the original one-byte species representation for the reference Core.** Establish a shared way to refer to a species as new code is written. Add an independently selectable two-byte species format when building the large-roster capability. Make that capability the first step of the large-roster work, ahead of mass data entry. The battle corrections, Charizard's Fly compatibility, a type-chart edit and a move retyping each work with the existing representation.

**Sixteen bits are enough for the nine-generation goal.** The official National Pokédex runs through Pecharunt at 1,025 for those generations. That count covers numbered species. Forms sharing a Pokédex number add engine identities if the project assigns them separate IDs. A single byte has 256 patterns. Ten bits have 1,024, already one short of 1,025 species even before reserving an empty value. Eleven bits cover the 1,026 values from 0 through 1,025. A two-byte identifier fits that range with room for explicitly assigned forms and custom species. Thirty-two bits would add two more bytes per identifier with no identified need. ID size alone says nothing about whether all the art, text, moves and maps fit on the target cartridge. [Official roster](https://press.pokemon.com/en/The-Pokemon-Company-International-to-Release-the-Pokemon-Deluxe-Charac)

## What the cartridge stores

The species value Red and Blue store for a Pokémon differs from its Pokédex number. Internal species 1 is Rhydon. A one-byte table maps it to its displayed Pokédex number. Historical empty entries, a shared trainer/species opponent field, an end marker in party and box lists, and the name lookup all use pieces of the byte range. The trainer boundary is 200. The name lookup independently treats values from HM01 (196) as machines and the build asserts that species indexes stay below it. These restrictions have separate fixes. A count of 255 available species would overstate the original interface. Stock reserves space for the active box in the main save and for 12 box records in two other SRAM banks. The latter are allocated slots. When changing boxes, the game copies one whole record and marks its source empty. These are space costs, independent of how many Pokémon a save currently holds. This direct design adds 492 bytes across the 12 stored boxes, another 41 to the active box and 13 to the party. A dense 1,025-entry Pokédex requires 129 bytes for each of seen and owned, an additional 220 bytes combined over 151 entries. The stock bit counter returns an eight-bit count and the standard flag helper takes an eight-bit bit index. Expanding the arrays alone would give incorrect counts or select the wrong flags. These figures exclude changes to other state, checksums, form tracking and ROM assets. Stock copies contiguous party and box bytes when saving and loading. Its Cable Club exchanges a block containing the player name, party list, six records, names and framing. The wide branch grew the list and records. Its cable transfer length still counts the list as one byte per slot plus a one-byte terminator. The compiled party-exchange instruction requests 424 bytes in stock and 430 in the wide branch. Keeping the same six preamble bytes, eleven-byte player name and three trailing bytes around the complete widened party would require 437. The seven-byte shortfall equals the extra bytes in the species list. These figures describe one block of the exchange. The branch's November 2026 fix author explicitly left link trades and battles unresolved. The measured result is a successful build and a layout comparison. Save conversion, a high-ID playthrough and multiplayer require separate tests. Kanto Expansion Pak's author independently documents omitting baby Pokémon and regional pre-evolutions because the one-byte roster was full. These are concrete cases for providing a maintained large-roster feature and keeping wire compatibility a separate engineering task. The width of a species ID also has no bearing on the four move IDs in its battle record. The wide branch keeps each move slot at one byte. Supporting more move IDs requires a separate change to move slots and consumers. A type ID is another field. The stock damage code compares that ID with the numeric boundary for special attacks. Adding a type such as Fairy requires an explicit category under Gen 1 rules, plus its name and matchups. Retyping an existing move requires testing its resulting physical or special category even when all IDs still fit one byte. ## How the shared code should work

1. **Use one species definition.** Give each species a stable project identity, its Pokédex number if applicable, and its stock byte ID where one exists. Describe optional forms and their relationship to species explicitly. A saved identity must keep its meaning when another family is disabled or inserted. A ROM table may be densely packed for a particular build if the game can translate its stored IDs. Use a separate value or tag for trainer opponents. Define how an empty slot or end of a list is represented.
2. **Keep format choices at the points that read or write IDs.** Use shared data macros and small routines for authoring encounters, looking up Pokémon, reading records, saving and exchanging a party. Start with paths touched by actual features. Keep compact code for Minimal and Core. The wide build may use register pairs and banked tables where needed. Share the battle rule and event logic. Compare a direct two-byte implementation with a smaller encoded representation only if measured WRAM, SRAM or frame time requires it.
3. **Keep the roster, rules and binary format independently identifiable.** A build selects species/families, mechanics and a supported storage format. Reject a compact build if any enabled identity or required reference cannot be represented, even when the roster is small. Check evolution targets, encounters, gifts, trainers and forms when compiling. Either include a required dependency or report the exact referring entry. Adding Fairy does not require two-byte species IDs. Adding later moves, items or ROM banks needs separate capacity work. The current one-byte bank helper and the cartridge mapper have their own limits. [Existing hardware budget](../docs/02-architecture.md#memory-and-capacity) · [Stock bank switch](https://github.com/pret/pokered/blob/ba9c0568f64ae602fadda577a08c66639f93082a/home/bankswitch.asm#L1-L35)
4. **Make compatibility explicit.** Give a widened save its own format version and a roster identity mapping. Translate and validate a whole imported save before writing it. Cover the active box, every stored box, Day Care, Hall of Fame, Pokédex and story state carrying a species. Detect an unknown or disabled identity and leave the input safe. Keep original bytes in the compact format where compatibility is promised. For link play, specify the wire format, allowed species and move mappings, plus the rules needed for battles. Gate any claim of vanilla trades, matched-build battles or mixed-build play on its own two-peer tests.
5. **Provide one resolved build configuration.** Expand a named preset into visible rules and capabilities. Apply documented developer overrides and check dependencies before assembly. Record the effective choices, save layout and link compatibility in a build manifest. Use named settings for decisions a developer might reasonably want independently. Share inseparable internal changes behind one capability. Neither the assembler's choice of register width nor the number of bytes in a record belongs in a player options menu.

Pokéemerald Expansion gives a useful example of the separation between roster content and game rules. At `10e22cf9`, its generation groups default on, families can be selected individually and updated species types have their own setting. Its National Dex limit depends on the highest enabled generation. The authors warn that changing this can require a new save. It demonstrates why two projects built with the same engine may have incompatible saves. Its configuration and the earlier [Emerald comparison](expansion-configuration.md) establish documented capabilities. Neither measures its share of Emerald hacks or establishes Game Boy resource costs. ## When to implement and accept it

| Stage | Required evidence |
|---|---|
| First Core | Preserve the six-member party, 20-slot boxes and stock species IDs. Compare party/box bytes, Pokédex flags, restored saves, battle outcomes and intended Red/Blue differences. Keep Green at Blue's gameplay settings. |
| First large-roster prototype | Build the same 151-species content with both encodings. Then add one test species above 255 and a lower ID with the same low byte, such as 257 and 1. Check encounter, capture, party/box transfers, naming, STATS, trainer battle, evolution, Transform, faint, save/load and Dex seen/owned. Include the 255/256 boundary, tall Pokédex indices and end-of-list values. Restore a real compact save through explicit conversion or state that conversion is unsupported. |
| Before adding whole generations | Measure memory and CPU time with a representative sprite, audio and learnset workload, including the largest bank and slowest tested lookup. Exercise IDs 1,023, 1,024 and 1,025, a four-digit Dex display, count and scroll, and save/reload across every box. Test both link roles with matching and incompatible peers, and version pairs with changed or disabled families. Confirm portable hardware or emulator support for any change of mapper. |
| Public developer feature | A developer can add a species without hand-editing parallel tables, choose a roster without enabling modern AI or modern battle rules, and add new data without renumbering existing saved species. Publish supported import/link combinations and the tested content budget. The full nine-generation roster requires a real build and data validation. |

**Reproducing the size comparison.** Build `pokered.gbc` and `pokeblue.gbc` in each pinned checkout with RGBDS 1.0.4. In each color's symbol file, subtract `wPartyMon1Species` from `wPartyMon2Species` and `wBoxMon1Species` from `wBoxMon2Species`. Compare `wPartyDataStart` to `wPartyDataEnd`, `wBoxDataStart` to `wBoxDataEnd`, and each species-list label to the following records label. For the wire count, inspect the immediate operand of `ld bc` after the loads of `wSerialPlayerDataBlock` and `wSerialEnemyDataBlock` in `CableClub_DoBattleOrTradeAgain`. It is hexadecimal 01A8 in stock and 01AE in the wide branch. The stock ROM SHA-1 values were `ea9bcae617fdf159b045185467ae58b2e4a48b9a` (Red) and `d7037c83e1ae5b39bde3c30787637ba1d4c48ce2` (Blue). The wide branch produced `33587159230de3101f5f6c80850d89e252b35dbd` (Red) and `a29e3940cb0203f7c2944975af5e285967357c8b` (Blue).
